```css
.hero-title span {
```

## ㊸ 白板首帧闪烁修复（2026-09-08 夜）
- **问题（用户实机反馈）**：点击白板功能界面在深色/浅色模式下都闪一下白 → 变回灰色；深色更刺眼。
- **根因（代码侦查 + bundle 实证）**：Excalidraw 0.17 的 `viewBackgroundColor` 默认 `COLOR_PALETTE.white`（在 `getDefaultAppState` 处），主画布背景由 `renderScene` 的 fillRect 绘制在 `<canvas>` 像素里（不可用 CSS 盖），变更必须走 `api.updateScene` 路径。我们注入暗色（#0D0F15）在 `handleAPI` 的 rAF 调 `engine.loadDocument(initialDocument)` → `api.updateScene` 才生效。挂载首帧 Excalidraw 内部 appState.theme/theme prop 同步也是异步（首帧可能仍以 light 渲染）。→ mount 到 rAF 注入暗色之间有 1~2 帧白色画布，**dark 主题 chrome 暗底反衬下白闪刺眼**；headless 截图证实稳态也偶发白残留（之前 px-canvas 76.9 万像素 (223,224,229) 白——实际是 rAF 时序在 headless 虚拟时间下让注入在截图前被冲掉/未生效；现在 booted 门闸后稳态 99.4 万像素全 #0D0F15 (13,15,21)）。
- **修复**：
  1. **`ExcalidrawCanvas` 加 booted 门闸**：`useState(booted)`，host `style.opacity = booted ? 1 : 0; transition: opacity 140ms ease-out`；handleAPI rAF#1 内 `loadDocument + onReady`，rAF#2（**双 rAF**）才 `setBooted(true)`——让 Excalidraw 用注入的暗色 viewBackgroundColor 完成重绘后再亮出，首帧即暗。卸载 `aliveRef` 守卫避免 setState 警告。
  2. **Aurora `canvas.css` `.aurora-canvas__viewport` 加 `background: #0D0F15`**——门闸透明期（opacity:0）露出 viewport 底色即与画布统一暗色，杜绝 chrome 暗底透出。
- **验证**：tsc=0；定向 smoke 7/7；全仓 vitest 770/1fail(预存 blogCssRefs)/2 skip = 基线一致；headless 像素对比（warm profile 双跑+不同 budget）：早期帧(budget 2200)与稳态(budget 9000)逐像素相同，画布区 100% #0D0F15，无白帧泄漏。
- **设计原则**：**视觉缺陷修复要思考底层逻辑（不止被点名的现象）**。本批不只是"用户说闪白"就 add opacity；先 grep 库内 default + 渲染路径（fillStyle vs CSS 背景、theme 同步时序）弄清白来自哪一帧、能否 CSS 兜底，再选最小侵入修复（门闸 + 兜底背景都是结构层的，不引入新依赖、不改数据流）。

## ㊹ 白板回归修复（StrictMode 兼容 + 容错兜底，2026-09-08 夜）
- **用户实机报障**：「现在白板功能使用不了了，空态引导弹窗消失，整个功能使用不了」，控制台 `Permissions policy violation: unload is not allowed`。
- **真根因**（不只看控制台那条 violation——那是 useAppLogic S6 beforeunload 在受限 iframe 文档下被 permission policy 静默拦截的纯 warning，与本批无关）：
  1. **StrictMode double-mount 钉死 aliveRef**——aurora-main.tsx L83 用 `<StrictMode>`，dev 下 effects 走 `mount→cleanup→mount`；上一批加的 `useEffect(() => () => { aliveRef.current = false }, [])` 在第一次 cleanup 后 aliveRef 恒 false，第二次 mount 的 handleAPI rAF 链 `if (aliveRef.current)` 全部被拦死 → `onReady` 不上报（engine 永 null → Dock/空态引导/缩放/右键/Dock/命令面板全部消失）+ `setBooted` 不执行（host 永远 opacity:0 透明）。headless 时序侥幸能亮，实机慢机器/Excalidraw bundle 首载节奏必现。
  2. **loadDocument 异常路径无兜底**——handleAPI rAF 调 `engine.loadDocument(initialDocRef.current)` 无 try/catch，若真实历史白板数据（用户 IndexedDB 中）含异常元素/缺字段抛错，会跳过整个 ready + 双 rAF → 同上症状。
- **修复**（三处）：
  1. `aliveRef` effect body 重置 `aliveRef.current = true`——使 StrictMode 第二次 mount 也能注册可执行的 rAF 链（兼容 React 18 dev double-invoke 的真实语义：mount 后 alive，而非实例创建时 alive）。
  2. `loadDocument` 包 try/catch（异常 → `console.warn` 降级空白画布，不阻断 ready/booted）。
  3. `booted` 加 1500ms `setTimeout` 超时兜底 effect——rAF 链被任何原因卡住（后台 tab rAF 暂停等）时强制亮出，保证「永不永黑」的最坏情况是退回修复前的表现。
- **验证**：tsc=0；canvas smoke 4/4；**headless 实测空态引导恢复**（截图见 v2-canvas.png：引导卡片「白板还是空的 / 新建便签 / 文件便签 / 跳过，直接开始」+ Dock 头像 + 缩放 + Aurora 侧栏全套 chrome 完整渲染）——证明 StrictMode 修复 + onReady 恢复全部生效。全仓 vitest 后台跑。
- **附带观察（非紧急·记待打磨）**：v2 profile 全新首跑截图里画布区主色是 Excalidraw native 暗底 #121212 而非我们统一 #0D0F15（差 ~5/255 不可分辨），疑 Excalidraw 在空场景时用 `var(--default-bg-color)` 作 CSS 层兜底覆盖我们的 viewBackgroundColor 注入。子视图与画布基线差异 <10 视觉不可见，不阻塞交付；如需像素级统一，下批可在 excalidraw-hide-ui.css 给 `.excalidraw-canvas-host` 加 `background: #0D0F15 !important` 兜底（Excalidraw 背景画在 canvas 像素层而非 DOM 背景，但加兜底可在某些时序仍看到画布就显深色）。
