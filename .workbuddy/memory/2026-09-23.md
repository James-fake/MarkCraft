## 第八轮 · 博客待发布清单混入内置《MarkCraft 使用文档》（用户报障）

**报障原话**：「点击进入到博客功能，预览界面中的博客文章会显示 Markcraft 使用文档知识库中的笔记，
现在文件列表中的没有这些笔记文件，要求从博客文章中删除。」

### 根因（一句话）
博客入口（无 `kbId`）的清单用 `collectMarkdownFiles(rootFolder)` 枚举**全部** `.md`，
没套用编辑器文件列表已在用的 `hiddenIds`（内置说明书过滤）。默认文件树里**唯一的 .md 恰是那 16 篇内置文档**
⇒ 全新用户的博客清单 **100%** 是应用说明书。

**反证（很有说服力）**：修好后跑既有 `BlogPanel.smoke.test.tsx`，**恰好 2 例失败**
（`docs.length > 1` 与「预览含 My Blog」）——这两个用例的夹具一直在**隐式依赖**那 16 篇内置文档当"文档清单"，
即：修复前它们测的就是被排除的东西。失败本身就是「泄漏是整体性的」证据，也说明夹具必须改成
**显式种入普通笔记**（同项目既有教训：夹具别取"第一个/默认就有的"）。

### 修法（严格复用单一数据源，不另写判定）
- `BlogPanel` 取 `useUsageDocsScope().hiddenIds`，在 `collectMdFiles(node, hiddenIds)` 里过滤；
  写法对齐 `FileTree#visibleRecent`（集合为空不额外分配数组）。
- **边界（有意为之，写进注释）**：知识库入口**不过滤** —— 其口径是「与该库详情页笔记列表完全一致」，
  而内置文档所在的库本身就是说明书的浏览入口；在此过滤会让**非空库显示成空库**，反而对不上详情页。

### 测试

  幂等是关键：B3 用例 4 段重挂若每次都建，`docs.length` 会在段间漂移、用例会为**错误的原因**红。
- 新增回归 1 条，四层齐备：① 扫描面非空（树里确有内置文档**且**它们确在隐藏集合内）

  ⚠️ 预览的文章标题取自**正文首个标题**（`# 甲` → 显示「甲」），**不是文件名** —— 故内置侧也按同一口径
  从数据取标题，别拿文件名当字面量（会漏判成假绿）。

## 第九轮 · 双链图谱「知识库范围」（用户报障）→ 已提交 91ede7d

**报障原话**：「现在要求功能去到双链图谱的界面，界面只显示这个功能的相关的内容，例如：现在 markcraft
使用文档知识库有图谱，点击查看完整图谱后去到双链图谱功能界面，但是会有文件列表中的文件在其中，
现在要求只要有这个知识库文件节点，你懂我的意思吗，不懂的话可以向我询问」

**用户拍板的三条边界**（AskUserQuestion，均取推荐项）：
① 范围 = **仅该库内文件节点**（库外文件一律不画；库内互链 + 库内笔记用到的标签保留）；
② 其他入口（侧栏「双链图谱」/ 菜单栏 / 命令面板）**保持全局图谱**；
③ 范围明示 = 顶栏范围芯片 + 面包屑「双链图谱 › XX 库」+ 一键「查看全局图谱」出口。

### 根因
图谱入口**没有范围参数**：`KbPanel` 概览只发 `nav('graph')` → `useAuroraShell` 的 param→params
映射表**未登记 graph** → `AuroraShell` 的 `case 'graph'` 不读 `kbId` ⇒ 图谱永远是全量树。

### 修法（沿单源，不新增机制）
- 传递链：`KbPanel#openFullGraph()`（kbId 拼接集中在此，哑组件不各自拼）→
  `useAuroraShell` 映射表补 `graph → { kbId }` → `AuroraShell` 按 `params.kbId` 传参。
- 裁剪纯函数 `scopeGraphToKb(data, kbFileIds)`：**两步法** —— ① 取库内文件；
  ② 由「一端是库内文件的边」收集被触达 tag；边两端都须落在 `库内文件 ∪ 本库tag` 内。
  库内文件用 `getKbFiles(rootFolder, kb)` **现取**（与博客清单 / KB 详情页同口径）。
- 范围隔离：`graphSession` 增 `kbId`，`readScopedSession(kbId)` 范围不符即视为无现场
  （否则全局图的视口/选中会串到范围图）。
- 往返闭环：范围内点开笔记 → `navReturn` 带 `kbId` + 「XX 库 · 图谱」→ 返回回**同范围**图谱。

### 🚨 本次最大的教训：**冷启动 dev server 会让对照运行整体失真**
第一次跑 HEAD 阳性对照得到 **14/30**，且 **§1/§2（本应保持绿的全局入口与知识库列表）也红** ——
这本身就是"对照无效"的信号。取证（同一浏览器里手动点侧栏）证明 **HEAD 侧栏点击完全正常**
⇒ 差异是 **worktree 里新起的 Vite 冷启动**：首次服务模块转换慢，探针在应用尚未可交互时点击，

## 第十一轮 · 双链图谱「节点拖拽」（用户报障：松手飞出去 + 不丝滑）

**请求**：「优化图谱功能的节点拖拽，快速滑动松手后有个别单独的节点飞的很远，且拖拽性能不够丝滑」。

### 根因（两个缺陷 + 一组性能瓶颈）
1. 🚨 **斥力奇点**：旧 `step()` 里两两斥力把 `d²` 夹到 1（`const d2 = Math.max(d*d, 1)`），
   但**幅值仍用原始 `dx/dy` 归一化** ⇒ 两节点近重合时 `dx/d` 的分母被夹小、分子不变，
   得到**万倍冲量**；被撞的节点瞬间获得巨大速度 = 「飞出去」。
2. 🚨 **拖拽速度残留**：被拖拽节点每帧照样参与积分、速度持续累积；`onPointerUp` 未归零 ⇒
   松手瞬间把整段甩动累积的动量一次性释放 ⇒ 「松手后飞很远」。
3. **性能**：`onPointerMove` 每帧做 `toWorld()` + `reheat(0.35)`（alpha 打满，全程满力模拟）；
   `getBoundingClientRect()` 每帧调用（强制同步重排）；`nodes.find()` 线性查找；
   CSS 过渡/脉冲/发光在拖拽期持续重绘。

### 修法（抽纯函数 + 三处根因修复 + 拖拽期降载）
- 力模拟抽成**纯函数** `simulateStep(p)`（`src/aurora/panels/kb/GraphPanel.tsx`，导出供测试）。
  参数：`REP=24000, LINK_DIST=140, LINK_K=0.035, GRAVITY=0.012, MIN_SEP=36, VEL_DECAY=0.86,
  MAX_STEP=16(导出), DRAG_ALPHA=0.2`。
  - ① `const eff = d < MIN_SEP ? MIN_SEP : d; const f = (REP/(eff*eff))*alpha`
    —— **必须用夹后的 `eff`** 同时参与归一化与幅值。
  - ② 被拖节点每帧 `vx = vy = 0`（钉住、不累积）；`onPointerUp` 亦**显式归零**。
  - ③ 单帧位移上限 `MAX_STEP`（任何极端力都不允许一帧瞬移）。
- 性能：`onPointerMove` 只登记 `dragPtrRef.current` + 确保 loop 在跑；
  `getBoundingClientRect()` 提到 `pointerdown` 缓存进 `dragRef.rect`；
  `nodeById` Map（`useMemo` 按 `graphRev`）替代 `nodes.find()`；
  新增 `.aurora-graph__svg.is-dragging`（`graph.css`）关闭 node/edge/dot/label 过渡、
  当前节点脉冲、活跃发光。

### 测试
- 新增 `src/aurora/panels/kb/graphForce.test.ts`（5 例纯函数）：奇点消除 / 近重合 30 步
  速度与位移有界 / 拖拽 20 帧速度恒 0 且位置严格跟手 / 松手后逐帧 ≤ MAX_STEP / 非力导向不吸附。

## 第十二轮 · 编辑器 WYSIWYG「高亮」工具点击色块无效（修复 + 真机验证）

**报障原话**：「现在编辑器功能的高亮工具，点击之后没有效果，请修复，修复完成后告诉我这个功能怎么使用」。

### 根因（一句话）
`WysiwygToolbar` 的高亮下拉「外部点击关闭」handler（`document.mousedown`）**只排除高亮按钮、未排除下拉面板本身**
⇒ 点击色块时 `e.target` 是色块（不在按钮内）→ handler 判为真·外部点击 → `setHighlightDropdownOpen(false)`
把面板在色块 `onClick`（执行 `setHighlight`）触发前卸载 ⇒ 表现为「点击无效果」。

## 第十二轮（续）· 高亮按钮「点了没反应」真因 = 下拉被工具栏 overflow:hidden 裁掉（二次修复）

**报障原话**：「现在编辑界面格式工具栏内高亮按钮点击之后还是没有任何反应。」

### 🚨 上一轮诊断走偏（纠正）
上一轮定位为「外部点击 handler 未排除面板 → 色块 click 落空」并已修（4831388）；用户复测仍无反应
⇒ 真因是**可见性**：高亮下拉面板以 inline `position:absolute` 留在工具栏内部，而 `.wysiwyg-toolbar`
容器带 `overflow:hidden` ⇒ 面板**已挂载、却被裁掉、屏幕上不可见** = 「点了没任何反应」。
（色块 click 链路只是次生问题，把它当主因属误判。）

### 修法（对齐单源）
改用工具栏内其它下拉的既有范式：`createPortal(..., document.body)` + `position:fixed` + `useDropdownPosition`
（对齐 `WysiwygHeadingDropdown` / `ListDropdown` / `MoreDropdown`）。工具栏内**唯一**用 inline absolute 的
交互下拉就是这个（另一处 `position:absolute` 是装饰性 accent 线，非交互，无需动）。

### 🚨 探针教训（最重要）：只断言「在 DOM」= 裁切类 bug 的假绿
上一轮探针 §3 只查 `!!document.querySelector('div[title="yellow"]')` —— 面板被裁掉时它**依然 true**
（挂载了，只是不可见）⇒ 探针全绿而用户仍报障。本轮新增 §3b「**屏幕上可命中**」判据：
`document.elementFromPoint(色块中心)` 命中色块 ∧ `insideToolbar=false` ∧ `panelParent=BODY`。
- HEAD(v1 inline)：§3b **翻红**（isSwatch=false, insideToolbar=true）→ 精确复现用户症状。
- 修复版(v2 portal)：§3b **绿**（isSwatch=true, insideToolbar=false, panelParent=BODY）。
通则：**「元素在 DOM 里」≠「用户看得见」**。凡「点了没反应」类报障，探针必须断言**可命中性/可见性**
（`elementFromPoint` 或 `getClientRects` + 祖先裁剪判定），不能只数 DOM 节点；也别拿「看得见」当 DOM 存在的同义词。
