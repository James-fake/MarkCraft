## 第八轮 · 博客待发布清单混入内置《MarkCraft 使用文档》（用户报障）

**报障原话**：「点击进入到博客功能，预览界面中的博客文章会显示 Markcraft 使用文档知识库中的笔记，
现在文件列表中的没有这些笔记文件，要求从博客文章中删除。」

### 根因（一句话）
博客入口（无 `kbId`）的清单用 `collectMarkdownFiles(rootFolder)` 枚举**全部** `.md`，
没套用编辑器文件列表已在用的 `hiddenIds`（内置说明书过滤）。默认文件树里**唯一的 .md 恰是那 16 篇内置文档**
⇒ 全新用户的博客清单 **100%** 是应用说明书。

**反证（很有说服力）**：修好后跑既有 `BlogPanel.smoke.test.tsx`，**恰好 2 例失败**
（`docs.length > 1` 与「预览含 My Blog」）——这两个用例的夹具一直在**隐式依赖**那 16 篇内置文档当"文档清单"，
即：修复前它们测的就是被排除的东西。失败本身就是「泄漏是整体性的」证据，也说明夹具必须改成
**显式种入普通笔记**（同项目既有教训：夹具别取"第一个/默认就有的"）。

### 修法（严格复用单一数据源，不另写判定）
- `BlogPanel` 取 `useUsageDocsScope().hiddenIds`，在 `collectMdFiles(node, hiddenIds)` 里过滤；
  写法对齐 `FileTree#visibleRecent`（集合为空不额外分配数组）。
- **边界（有意为之，写进注释）**：知识库入口**不过滤** —— 其口径是「与该库详情页笔记列表完全一致」，
  而内置文档所在的库本身就是说明书的浏览入口；在此过滤会让**非空库显示成空库**，反而对不上详情页。

### 测试
- 夹具改为**按名幂等**种入 2 篇普通笔记（`FileStore` 是模块单例、跨用例累积，重挂 Harness 不能重复建）。
  幂等是关键：B3 用例 4 段重挂若每次都建，`docs.length` 会在段间漂移、用例会为**错误的原因**红。
- 新增回归 1 条，四层齐备：① 扫描面非空（树里确有内置文档**且**它们确在隐藏集合内）
  ② 零命中（清单无内置）③ 非空对照（自己种的笔记仍在）④ 预览同源（真实生成器产物不含内置正文）。
  ⚠️ 预览的文章标题取自**正文首个标题**（`# 甲` → 显示「甲」），**不是文件名** —— 故内置侧也按同一口径
  从数据取标题，别拿文件名当字面量（会漏判成假绿）。
- **注入探针验红**：把 `collectMdFiles(rootFolder, usageDocs.hiddenIds)` 改回 `collectMdFiles(rootFolder)`
  → 恰好新增那 1 条红（16 篇内置名泄漏进清单），其余 5 绿；随后字节级还原（sha 复核一致）。

### CDP 真机（新增 `.workbuddy/artifacts/cdp-verify-blog-exclude-usagedocs.mjs`）
- 修复版 **14/14 绿**；HEAD 阳性对照 **11/14 —— 恰好 §2 等式 / §3 零命中 / §5 预览三条翻红**，
  泄漏被抓满 **16 篇**内置文档（含真实标题「3. 文件管理」等）。§0 扫描面/对照面、§1 挂载、
  §2 清单非空、§4 错误 **全绿** ⇒ 红的理由是**行为差异**，不是页面没加载。
- 设计要点（v2 修正了 v1 的两个自欺点）：
  1. **内置文件名清单从 dev server 现取**（`curl http://127.0.0.1:5174/src/core/data/defaultDocs/usageDocs/zh.ts`
     + 正则抽 `fileName:`）—— 不硬编码。v1 只核对我自种的 4 篇，而真机上会有 **16 篇**在树里，
     12 篇不在检查范围内 ⇒ 零命中断言被削弱。
  2. **期望值在断言时刻重读树**，不用「播种后立刻读」的旧快照。v1 用旧快照（6 个文件）算期望，

  3. 「清单非空」与「清单 === N」**拆成两条**断言：焊在一起时 HEAD 上它会为**错误的原因**红（归因不诚实）。
- 🚨 **机制发现（值得记）**：真机上「替换整棵树」后，内置库的 `folderId` 会**悬空** →
  `kbSeed` 走**自愈**分支把内置文档**补齐到全量 16 篇**。该分支（`run()` ①：同名库存在但 folderId 解析不到）
  在「已播种」标记检查（②）**之前** ⇒ 设 `markcraft-usage-docs-seeded='1'` **挡不住补齐**。
  凡是「内置文档清单」的断言，一律**现取或全量核对**，别只核对自种的几篇。
- 探针侧踩坑：**`CDP_PORT` 必须与 Edge 启动端口一致**。我一轮把 Edge 起在 9466、探针默认 9444 →
  报 `fetch failed`，看起来很像"代理污染/端口没起"，实际只是端口没对齐。顺带实测：
  本机 `HTTP_PROXY` 对 **node fetch（undici）不生效**（`fetch` 200 正常）—— 别把它当坑 Y 误判。

### 边界与遗留（未动，供决策）
- 知识库入口（`kbId` 那条路）**有意不过滤**：若用户从内置库进博客，仍会看到那 16 篇。
  理由见上（保「与详情页一致」+ 避免非空库显示成空库）。若用户要的是"内置文档在任何入口都不可发布"，
  需要先改 KB 详情页的口径，再同步这里 —— **不要只改博客一侧**。
- 内置过滤后，全新用户（默认树只有说明书）在博客会看到空态文案
  `文件库中未发现任何 .md 文档` / 预览诊断 `（若编辑器侧边栏有文件，请反馈此信息）`——
  该文案原本只为"异常"场景设计，现在成了**新用户的正常状态**。是否改成友好引导，待用户决定（本轮未改，避免超范围）。

## 第九轮 · 双链图谱「知识库范围」（用户报障）→ 已提交 91ede7d

**报障原话**：「现在要求功能去到双链图谱的界面，界面只显示这个功能的相关的内容，例如：现在 markcraft
使用文档知识库有图谱，点击查看完整图谱后去到双链图谱功能界面，但是会有文件列表中的文件在其中，
现在要求只要有这个知识库文件节点，你懂我的意思吗，不懂的话可以向我询问」

**用户拍板的三条边界**（AskUserQuestion，均取推荐项）：
① 范围 = **仅该库内文件节点**（库外文件一律不画；库内互链 + 库内笔记用到的标签保留）；
② 其他入口（侧栏「双链图谱」/ 菜单栏 / 命令面板）**保持全局图谱**；
③ 范围明示 = 顶栏范围芯片 + 面包屑「双链图谱 › XX 库」+ 一键「查看全局图谱」出口。

### 根因
图谱入口**没有范围参数**：`KbPanel` 概览只发 `nav('graph')` → `useAuroraShell` 的 param→params
映射表**未登记 graph** → `AuroraShell` 的 `case 'graph'` 不读 `kbId` ⇒ 图谱永远是全量树。

### 修法（沿单源，不新增机制）
- 传递链：`KbPanel#openFullGraph()`（kbId 拼接集中在此，哑组件不各自拼）→
  `useAuroraShell` 映射表补 `graph → { kbId }` → `AuroraShell` 按 `params.kbId` 传参。
- 裁剪纯函数 `scopeGraphToKb(data, kbFileIds)`：**两步法** —— ① 取库内文件；
  ② 由「一端是库内文件的边」收集被触达 tag；边两端都须落在 `库内文件 ∪ 本库tag` 内。
  库内文件用 `getKbFiles(rootFolder, kb)` **现取**（与博客清单 / KB 详情页同口径）。
- 范围隔离：`graphSession` 增 `kbId`，`readScopedSession(kbId)` 范围不符即视为无现场
  （否则全局图的视口/选中会串到范围图）。
- 往返闭环：范围内点开笔记 → `navReturn` 带 `kbId` + 「XX 库 · 图谱」→ 返回回**同范围**图谱。

### 🚨 本次最大的教训：**冷启动 dev server 会让对照运行整体失真**
第一次跑 HEAD 阳性对照得到 **14/30**，且 **§1/§2（本应保持绿的全局入口与知识库列表）也红** ——
这本身就是"对照无效"的信号。取证（同一浏览器里手动点侧栏）证明 **HEAD 侧栏点击完全正常**
⇒ 差异是 **worktree 里新起的 Vite 冷启动**：首次服务模块转换慢，探针在应用尚未可交互时点击，
**点击不生效**（不是没渲染，是点了没反应）。
- 判据：`§0 应用外壳就绪 waitIdx` —— 主仓（热）**0**，worktree（冷）**16**（≈8s）。
- 修法：给对照加**预热轮**（同一浏览器里先走一遍图谱 / 知识库路径，让 Vite 完成转换），
  之后 §1/§2 恢复正常，对照变成 **18/30**。
- ⚠️ 教训一般化：**"对照大面积翻红（连本应绿的门也红）"要先怀疑对照运行条件，而不是庆祝灵敏**。

### 🚨 另一类坑：**对照的"翻红"可能来自探针自己的新锚点**
本次修复顺带给图谱节点加了 `data-node-id` / `data-node-type`（label 只在孤立/热点/悬停节点渲染，
无法做身份级定位）。⇒ HEAD 上没有这些锚点，`GRAPH_FILE_IDS` **恒为空**，
于是 §1/§3/§5/§6 里所有"数数 / 身份"断言在 HEAD 必然红 —— **红的原因不全是行为差异**。
补了一个**不依赖新锚点**的泄漏取证（直接数 `.aurora-graph__node`）：
HEAD 上 **N_all=23 === N_kb=23**（从知识库进入的图 = 全局图）⇒ 库外文件确实没被裁剪、
报障真实存在、且**数数法能量到该差异**。这样"核心断言在 HEAD 会红"才算有真凭据。
- 可归因清单（HEAD 18/30）：§4 三条（范围芯片 / 面包屑库名 / 出口按钮）**纯行为差异**；
  其余因缺锚点或依赖出口按钮。

### 🚨 第三类坑：**传给原生 exe 的路径必须 Windows 风格**（本轮踩到两次）
- `msedge.exe --user-data-dir=/c/Users/...` → Edge 收到非法值 → 回落**默认 profile**
  → 委派给用户正在跑的 Edge 实例。症状：**CDP 端口根本不监听**，日志只有
  「正在现有浏览器会话中打开」；看起来像"端口没起/被占用"。
- `node.exe /c/Users/.../x.mjs` → 被解析成 **`D:\c\Users\...`**（相对当前盘）。
- 正解：脚本内同时维护 `/c/...`（给 bash 的 rm/ls）与 `C:/...`（给 node/edge）两份路径。
- 另：`.mjs` 放 `%TEMP%` 时**解析不到仓的 `ws`**（ESM 包解析基于脚本自身位置，`NODE_PATH` 对 ESM 无效）
  → 探针脚本必须放进仓内（用完即删）。
